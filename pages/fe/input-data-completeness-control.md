## まず結論

入力データの監査では、**何を確かめたいのか**を先に見ます。

特に重要なのは、次の切り分けです。

```text
入力された値は正しい？
→ 正当性

入力すべきものが全部入った？
→ 完全性

同じものが重複していない？
→ 一意性
```

起票された伝票が**漏れなく、重複なく**入力されたことを確かめたいなら、原始伝票と入力結果を照合できる方法を選びます。

その代表例が、**プルーフリストと原始伝票の照合**です。

## 直感的な説明

10枚の受注伝票をシステムへ入力するとします。

入力されたデータの形式がすべて正しくても、9枚しか入力されていなければ「漏れ」があります。

また、10枚すべて入力されていても、1枚を2回入力していれば「重複」があります。

```text
元の伝票
A B C D E

入力結果
A B C   E
      ↑
      Dがない
→ 完全性の問題

入力結果
A B C D D E
        ↑
        重複
→ 一意性の問題
```

そこで、

```text
原始伝票
   ↕ 照合
入力結果の一覧
```

として確認します。

## 定義・仕組み

### 完全性

完全性は、**入力すべきデータが漏れなく入力されていること**です。

例えば、100枚の受注伝票が起票されたなら、100件すべてが処理対象になっているかを確認します。

### 一意性

一意性は、**同じデータが意図せず重複して処理されていないこと**です。

伝票番号などを使って重複を検出する方法もあります。

### 正当性

正当性は、入力された値や形式が業務ルールに合っているかという観点です。

例えば、

```text
日付の形式は正しい？
→ フォーマットチェック

注文日と入力日の関係に矛盾はない？
→ 論理チェック
```

といった確認です。

入力値のチェックについては、[入力データのチェックとは？](/fe/input-data-check/)も参照してください。

### プルーフリスト

プルーフリストは、入力したデータを確認するために一覧として出力したものです。

原始伝票とプルーフリストを照合すれば、

- 入力されていない伝票がないか
- 同じ伝票が重複していないか
- 入力内容が原票と対応しているか

を確認できます。

FEでは、細かな帳票形式よりも、

> **元の資料と入力結果を突き合わせる → 漏れ・重複を確認する**

という役割を押さえることが重要です。

## 科目Aでどう出る？

問題文で、

> 「漏れなく、重複することなく入力されていることを確かめる」

とあれば、まず**完全性・一意性の確認**だと判断します。

次に、選択肢が何を確認しているかを分けます。

| 手続・方法 | 主に確認しているもの |
|---|---|
| 原始伝票とプルーフリストを照合 | 入力の漏れ・重複 |
| 論理チェック | 項目間の矛盾 |
| フォーマットチェック | 入力形式 |
| 例外取引の承認記録を確認 | 例外処理・承認 |
| プログラムのテスト | 処理ロジックの正確性 |

試験では、**方法の名前より「何を確認できるか」**で選択肢を切ります。

## どんな場面で使う？

販売管理、購買、会計など、伝票や申請データをシステムへ入力する業務で重要になります。

例えば、

```text
受注伝票
→ 販売管理システム

請求書
→ 会計システム

申請書
→ ワークフローシステム
```

といった処理です。

入力時のチェックだけでなく、入力前の資料と入力後の結果を照合することで、処理全体として漏れや重複がないか確認できます。

## よくある誤解・混同

### 論理チェックやフォーマットチェックをすれば、入力漏れも分かる？

必ずしも分かりません。

例えば、9件のデータがすべて正しい形式でも、本来10件入力すべきなら1件不足しています。

```text
入力された9件
→ 全部形式は正しい

しかし

本来は10件
→ 1件入力漏れ
```

つまり、**入力されたデータの正しさ**と**入力すべきデータが全部あること**は別の観点です。

### 重複チェックだけで完全性も確認できる？

重複チェックは同じデータが複数回入力されていないかを調べる方法です。

しかし、入力されなかったデータは入力結果だけを見ても分からない場合があります。

そのため、漏れを確認するときは原始伝票などの**入力元との照合**が重要です。

### プログラムが正しく動けば、入力の完全性も保証される？

プログラムのロジックが正しくても、入力すべき伝票そのものが入力されなければ漏れは発生します。

```text
プログラムの正確性
≠
入力データの完全性
```

ここを混同しないようにします。

## 一次情報で確認する

### IPAの基本情報技術者試験シラバス

FEで学ぶ知識・技能の範囲は、IPAの「基本情報技術者試験（レベル2）シラバス」で確認できます。現行版は **Ver.9.2** です。

- [IPA：試験要綱・シラバスについて](https://www.ipa.go.jp/shiken/syllabus/gaiyou.html)

### 経済産業省のシステム監査基準

経済産業省は、2023年4月に「システム監査基準」を改訂しています。

- [経済産業省：システム監査基準（2023年4月26日）](https://www.meti.go.jp/policy/netsecurity/sys-kansa/sys-kansa-2023r.pdf)

現在の基準は、システム監査の実施や報告を含む基本的な枠組みを示すものです。

過去問題では旧基準や当時の用語を前提とする場合がありますが、学習では**問題が何を確認しようとしているか**を現在の監査の考え方と切り分けて理解します。

今回のテーマなら、

```text
入力値は正しい？
→ 正当性

全部処理された？
→ 完全性

重複していない？
→ 一意性
```

という観点を優先します。

## まとめ（試験直前用）

- 「漏れなく入力」なら、**完全性**を見る
- 「重複なく入力」なら、**一意性**を見る
- 原始伝票と入力結果の照合は、漏れ・重複の確認に有効
- プルーフリストは、入力結果を原始伝票と照合するために使える
- 論理・フォーマットチェックは、主に入力された値の正当性を見る
- プログラムの正確性と入力データの完全性は別問題
- 迷ったら「その手続で何を確認できるか」を考える
