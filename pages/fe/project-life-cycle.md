## まず結論

**プロジェクトライフサイクルでは、開始から終結へ進むにつれて、リスクや不確実性は小さくなり、後から変更したときの影響やコストは大きくなる、と整理すると判断しやすくなります。**

基本情報技術者試験では、まず次の関係を押さえます。

| 見るもの | 開始時 | 実行中 | 終結に近い時期 |
|---|---|---|---|
| リスク・不確実性 | 大きい | ↓ | 小さくなる |
| 低コストで変更できる余地 | 大きい | ↓ | 小さくなる |
| 変更・手戻りの影響やコスト | 小さい | ↑ | 大きくなる |
| 要員数 | 少ない | 多くなりやすい | 少なくなる |

試験中の判断軸は、次の一文です。

> **先ほど不確実、後ほど変更が重い。**

なお、要員数はプロジェクトの種類や進め方によって異なります。試験では、典型的なライフサイクルとして「開始時と終結時は少なく、実行中に多くなる」という形を押さえます。

## 直感的な説明

家を建てるプロジェクトで考えてみます。

計画を始めたばかりの段階では、まだ決まっていないことが多くあります。

```text
開始時
→ 分からないことが多い
→ リスク・不確実性が大きい
```

しかし、この段階なら間取りを変更しても、まだ実際の建物を作っていないため、比較的小さな影響で済みます。

一方、完成直前に「部屋の位置を変えたい」となるとどうでしょうか。

```text
完成直前
→ 既に多くの作業が完了
→ 変更すると多くの部分をやり直す
→ 変更・手戻りの影響が大きい
```

つまり、プロジェクトが進むほど情報は増えて不確実性は減りますが、既に作ったものも増えるため変更しにくくなります。

```text
開始 ─────────────────→ 終結

リスク・不確実性
高い ───────────────→ 低い

変更しやすさ
高い ───────────────→ 低い

変更・手戻りの影響
小さい ─────────────→ 大きい
```

この「逆向きの関係」が重要です。

## 定義・仕組み

### プロジェクトライフサイクルとは

プロジェクトライフサイクルは、**プロジェクトの開始から終結までを一連の流れとして捉える考え方**です。

プロジェクトには開始と終了があり、その途中で計画、実行、管理などを行います。

FEの現行シラバスでは、「プロジェクトライフサイクル」がプロジェクトマネジメントの用語例として明記されています。

- [IPA：試験要綱・シラバス](https://www.ipa.go.jp/shiken/syllabus/gaiyou.html)

### リスク・不確実性はなぜ減る？

開始時は、まだ十分な情報がありません。

```text
開始時
→ 要求や条件に不明点がある
→ 将来の出来事を予測しにくい
→ 不確実性が大きい
```

プロジェクトが進むと、調査、設計、実行、確認などを通じて情報が増えていきます。

そのため、一般的には不確実性が減り、残っているリスクも少なくなっていきます。

ただし、**終盤なら新しいリスクが絶対に発生しない**という意味ではありません。

### 変更の影響やコストはなぜ増える？

プロジェクトの初期なら、まだ作っていない成果物が多いため、変更の影響範囲は比較的小さく済みます。

進行すると、既に作成した成果物や完了した作業が増えます。

```text
後半で変更
↓
完成済みの成果物に影響
↓
修正・再作業・再確認が必要
↓
変更の影響やコストが大きくなる
```

ウォーターフォール開発で上流工程の誤りが後工程へ及ぼす影響については、[ウォーターフォール型で上流工程の誤りほど修正コストが高い理由](/fe/waterfall-defect-correction-cost/)で詳しく整理しています。

### ステークホルダの影響力はどう考える？

初期段階では、まだ多くの内容が確定していないため、ステークホルダの要求を比較的小さなコストで反映しやすい状態です。

一方、プロジェクトが進むほど成果物や計画が具体化するため、同じ変更でも修正範囲が広くなりやすくなります。

試験では、

> **「コストを大きく変えずに影響を与えられる度合い」は初期ほど大きい**

と整理すると判断しやすくなります。

### 要員数は山型で考える

典型的なプロジェクトでは、開始時から全員が必要になるわけではありません。

```text
開始
→ 少人数で立ち上げ・計画

実行
→ 開発・作業が本格化して要員が増える

終結
→ 作業完了に伴い要員が減る
```

そのため、試験では要員数を「開始時が最大」と決めつけないことがポイントです。

## 科目Aでどう出る？

科目Aでは、プロジェクトの進行に伴って「増えるもの」と「減るもの」を入れ替えた選択肢が出題されます。

まず、次の2組に分けます。

```text
進むほど減る
→ リスク・不確実性
→ 低コストで変更できる余地

進むほど増える
→ 変更・手戻りの影響
→ 変更に必要なコスト
```

### 選択肢を切る判断表

| 選択肢の表現 | 判断 |
|---|---|
| リスクは終結に近づくほど減少する | 正しい方向 |
| 不確実性は終結に近づくほど増加する | 逆なので誤り |
| 後半ほど変更の影響が小さくなる | 逆なので誤り |
| 初期ほど低コストで変更しやすい | 正しい方向 |
| 開始時に要員数が最大になる | 誤りになりやすい |
| 終結直前ほど低コストで大きな変更ができる | 逆なので誤り |

迷ったら、次の順番で考えます。

```text
1. 「時間が進むとどうなるか」を問う問題か確認
2. リスク・不確実性か、変更の影響かを確認
3. リスクなら ↓
4. 変更の影響・コストなら ↑
```

## どんな場面で使う？

### リスク管理

プロジェクト初期は不確実なことが多いため、リスクを洗い出し、対応方法を考えます。

プロジェクトが進んだ後も、新しいリスクがないか継続して確認します。

### 変更管理

変更要求が出たときには、

```text
どの成果物に影響するか
どの作業をやり直すか
追加コストはいくらか
スケジュールへ影響するか
```

を確認します。

### 要員計画

プロジェクトの段階に応じて必要な要員やスキルが変わるため、最初から最後まで同じ人数を配置するとは限りません。

プロジェクトマネジメントの一般的な指針としては、ISO 21502:2020があります。ISOは、この規格が特定のライフサイクルモデルに限定されず、さまざまな種類のプロジェクトに適用できる指針であるとしています。

- [ISO 21502:2020：Project, programme and portfolio management — Guidance on project management](https://www.iso.org/standard/74947.html)

## よくある誤解・混同

### 終盤ほど情報が増えるから、リスクも増える

逆です。

情報が増えることで、分からなかったことが明らかになり、不確実性は一般に小さくなります。

```text
情報が少ない
→ 不確実性が大きい

情報が増える
→ 不確実性が小さくなる
```

### 完成に近いなら、変更する部分が少ないので影響も小さい

ここが典型的なひっかけです。

完成に近いほど、既に作ったものが多くあります。

そのため、一つの変更でも完成済みの成果物を修正したり、テストをやり直したりする可能性があります。

> **完成に近い = 変更が簡単、ではありません。**

### リスクが減るなら、終盤ではリスク管理は不要

違います。

一般的な傾向として不確実性や残存リスクが減るのであって、ゼロになるとは限りません。

終盤でも、問題の発生や新しいリスクの出現に備える必要があります。

### 開始時に要員を最大にすれば早く終わる

要員は、多ければよいわけではありません。

開始時には、まだ実行すべき作業が十分に展開されていない場合があります。

試験では、典型的な形として、

```text
開始時：少ない
実行中：多い
終結時：少ない
```

と捉えます。

### 「変更コスト」と「リスク」を同じ方向で考える

この2つは逆方向です。

```text
開始 → 終結

リスク・不確実性
      ↓

変更・手戻りの影響
      ↑
```

ここを入れ替えた選択肢に注意します。

## まとめ（試験直前用）

- プロジェクトライフサイクルは、開始から終結までの一連の流れ
- リスク・不確実性は、一般に開始時が大きく、進行とともに小さくなる
- 低コストで変更できる余地は、初期ほど大きい
- 変更・手戻りの影響やコストは、後半ほど大きくなりやすい
- 要員数は、典型的には開始時と終結時が少なく、実行中に多くなる
- 「リスク」と「変更の影響」は逆方向と覚える

試験直前には、次の一文を思い出してください。

> **先ほど不確実、後ほど変更が重い。**
