## まず結論

入力データのチェックは、入力された値や必要な項目が、形式・範囲・業務ルールに合っているかを確かめる仕組みです。**何を検出したいのか**で切り分けると迷いにくくなります。

| 見つけたい誤り | 判断しやすいチェック |
|---|---|
| 必要な項目が入力されていない | 必須チェック・項目数の確認 |
| 数値欄に文字が混じっている | ニューメリックチェック |
| 文字種・桁数・日付形式が違う | フォーマットチェック |
| 値が許容範囲を外れている | リミットチェック・レンジチェック |
| 項目同士の意味に矛盾がある | 論理チェック |
| 入力されたコードが登録済みか確認したい | マスタ照合 |
| 同じデータが二重登録されている | 重複チェック |
| 番号やデータの順番に抜けがある | シーケンスチェック |

FE科目Aでは、チェック名を丸暗記するよりも、**「抜け・形式・範囲・関係・照合・重複・順番」のどれを見ているか**を判断するのがポイントです。

> **入力漏れなら、まず「必要な項目がそろっているか」を確認する。**

## 直感的な説明

申込フォームをイメージすると分かりやすいです。

```text
氏名        ：山田太郎
生年月日    ：1990-04-15
会員区分    ：A03
購入数量    ：5
メール      ：未入力
```

このデータには、いろいろな種類のチェックが考えられます。

```text
メールが未入力
→ 必須チェック

生年月日が YYYY-MM-DD になっているか
→ フォーマットチェック

購入数量が 1～100 の範囲か
→ 範囲チェック

会員区分 A03 が会員区分マスタに存在するか
→ マスタ照合
```

重要なのは、**「データが正しいか」という一言でも、何を確認するかによってチェック方法が違う**ことです。

## 定義・仕組み

入力データのチェックは、誤ったデータや不足したデータがシステムに登録されるのを防ぐために行います。

代表的なチェックを整理すると、次のようになります。

| チェック | 確認するもの | 例 |
|---|---|---|
| 必須チェック | 必要な値が入力されているか | 氏名が空欄ではないか |
| 項目数の確認 | 必要な項目がすべて存在するか | 10項目必要なのに9項目しか入力されていない |
| ニューメリックチェック | 数値として正しい入力か | 数量欄に「12A」が混ざっていないか |
| フォーマットチェック | 書式・文字種・桁数など | 郵便番号が7桁か、日付形式が正しいか |
| リミットチェック | 上限または下限の一方を守るか | 数量が100以下か |
| レンジチェック（範囲チェック） | 上下の境界の間にあるか | 数量が1～100か |
| 論理チェック | 複数項目の関係や意味の矛盾 | 開始日が終了日より後になっていないか |
| マスタ照合 | 入力値が登録済みの値か | 商品コードが商品マスタに存在するか |
| 重複チェック | 同じデータの存在 | 同じ伝票番号が既に登録されていないか |
| シーケンスチェック | 順番・連続性 | 101、102、103…と並んでいるか |

### 必須チェック・項目数の確認

入力漏れを見つけたい場合は、**本来必要な項目が存在するか**を確認します。

例えば、伝票の様式ごとに必要な項目数が決まっているとします。

```text
必要項目数：8
入力項目数：7

→ 1項目不足
→ 入力漏れの可能性
```

この場合、データ形式を確認しても、すでに入力されている値の形式しか分かりません。

**入力されなかった項目そのものを見つけるには、必要な項目がそろっているかを見る必要があります。**

### フォーマットチェック

入力値の**書式や形式**が正しいかを確認します。

例：

- 日付が決められた形式になっているか
- 商品コードが英字2文字＋数字4桁になっているか
- コードの桁数が正しいか

「見た目・書式・文字種」を確認しているなら、フォーマットチェックを考えます。

### ニューメリックチェック

入力値が**数値として正しい形式か**を確認します。例えば数量欄に `12A` が入っていれば、文字が混ざっていることを検出します。数値として読めても許容範囲を外れている場合は、別に範囲の確認が必要です。

### リミットチェックとレンジチェック

数値などが、あらかじめ決めた範囲内にあるかを確認します。

```text
購入数量は 1～100
入力値は 150
→ 範囲外
```

形式として数値であっても、業務上あり得ない値なら範囲チェックで検出できます。

**リミットチェックは上限または下限の一方、レンジチェックは上下両方の境界**に注目します。例えば「100以下か」はリミット、「1～100か」はレンジです。名称の使い方には幅があるので、試験では問題文が示す検査条件を優先します。

### 論理チェック

**関連する複数の項目を比較し、意味として矛盾していないか確認するチェック**です。

例：

- 開始日 ≤ 終了日になっているか
- 貸出日 ≤ 返却日になっているか
- 販売数量が在庫数量を超えていないか

ポイントは、単独の値ではなく**項目同士の関係**を見ることです。

### マスタ照合

入力されたコードや値が、マスタファイルに登録されているかを確認します。

例えば、商品コード `P105` を入力したときに、商品マスタに `P105` が存在するかを確認します。

```text
入力値：P105
      ↓ 照合
商品マスタ：P101 / P102 / P105 / P108
      ↓
存在する → 登録済みの商品コード
```

マスタ照合で分かるのは、**入力された内容が登録済みの正しい候補かどうか**です。

入力されていない項目の存在そのものを確認するチェックではありません。

### 重複チェック

同じデータが既に存在し、**二重登録になっていないか**を確認します。

例：

- 同じ伝票番号が登録済みではないか
- 同じ会員番号が二重に登録されていないか

「同じものがあるか」が判断の軸です。

### シーケンスチェック

データが**決められた順番や連続した並び**になっているかを確認します。

```text
101 → 102 → 103 → 104
```

のはずが、

```text
101 → 102 → 104
```

となっていれば、103の抜けを検出できます。

このテーマはシステム開発やテストに関係する内容です。公式の出題範囲やシラバスは、[IPA：基本情報技術者試験](https://www.ipa.go.jp/shiken/kubun/fe.html) から確認できます。

### チェックディジットはどこが違う？

**チェックディジット（check digit）**は、識別番号などに規則的な検査用の桁を加え、入力ミスや転記ミスを検出する方法です。番号が実在するか、本人のものか、悪意ある改ざんがないかを保証する仕組みではありません。

計算方法や余り（mod）の問題は[チェックディジットの記事](/fe/check-digit/)で扱っています。

### クライアント側のチェックだけで十分？

十分ではありません。ブラウザ上の入力チェックは利用者のミスを早く伝えるために便利ですが、回避できる場合があります。[OWASPの入力値検証ガイド](https://cheatsheetseries.owasp.org/cheatsheets/Input_Validation_Cheat_Sheet.html)が示すように、**サーバ側でも必要な妥当性検査を行う**ことが大切です。

## 科目Aでどう出る？

科目Aでは、チェック名そのものよりも、**説明文からどのチェックが適切かを判定する問題**に注意します。

問題文を読んだら、次の順番で考えると切り分けやすくなります。

1. 入力されていない項目を探しているか
2. 書式や文字種を見ているか
3. 値の範囲を見ているか
4. 複数項目の関係を見ているか
5. マスタに存在するかを見ているか
6. 同じデータの有無を見ているか
7. 順番や欠番を見ているか

### 入力漏れを確認したい場合

「入力漏れがないこと」を確認したいなら、**内容の正しさではなく、必要な項目がそろっているか**を見ます。

```text
必要項目数と入力項目数を比較
→ 入力漏れを発見しやすい
```

一方、次の方法は別の目的です。

```text
データ形式を確認
→ 入力済みデータの形式を確認

マスタと照合
→ 入力済みデータの妥当性を確認
```

「入力された値が正しいか」と「入力そのものが抜けていないか」を分けて考えるのがポイントです。

### 日付を扱う問題では「何を見ているか」を確認する

例えば、

> 日付が `YYYYMMDD` の8桁で入力されているか確認する

なら、フォーマットチェックです。

一方、

> 開始日が終了日以前の日付になっているか確認する

なら、日付形式ではなく**二つの日付の関係**を見ているので論理チェックです。

### 確認問題

工場の点検記録で、点検開始日時と終了日時はいずれも正しい日付形式だが、終了日時が開始日時より前であることを検出したい。最も適切なチェックはどれか。

- ア：ニューメリックチェック
- イ：論理チェック
- ウ：フォーマットチェック
- エ：チェックディジット検査

<details markdown="1">
<summary>正解と解説を見る（タップして開く）</summary>

**正解：イ（論理チェック）**。個々の入力の形式は正しくても、2項目の前後関係という業務上の条件が成り立っていません。

</details>

## どんな場面で使う？

入力チェックは、注文管理、在庫管理、会員登録、会計、予約システムなど、データ入力を行う多くのシステムで使われます。

入力時点で誤りを検出できれば、後続処理で不正なデータが使われるのを防ぎやすくなります。

実際のシステムでは、一つのチェックだけでなく、複数のチェックを組み合わせます。

```text
必須チェック
↓
フォーマットチェック
↓
範囲チェック
↓
マスタ照合
↓
論理チェック
```

このように段階的に確認すると、入力漏れと内容の誤りを別々に検出できます。

入力時だけでなく、処理途中や出力後まで含めて「どの段階で何を確認するのか」を整理したくなったら、[コントロールトータルチェック](/fe/control-total-check/)も確認すると、入力値のチェックと、送受信・処理前後の合計照合の違いを整理しやすくなります。

さらに、入力・処理・出力の流れ全体を比較したい場合は、[SGの「入力・処理・出力チェックの違い」](/sg/input-process-output-checks/)を見ると、エディットバリデーション、ランツーランコントロール、コントロールトータルまでつながって理解できます。

## よくある誤解・混同

### 入力漏れはフォーマットチェックで見つけられる

フォーマットチェックは、**入力された値の形式**を確認します。

項目そのものが存在しなければ、形式を確認する対象もありません。

```text
項目がない
→ 必須・項目数を見る

項目はあるが書式が違う
→ フォーマットを見る
```

### マスタ照合をすれば入力漏れも分かる

マスタ照合は、入力された値がマスタに登録されているかを確認するものです。

```text
商品コード P105 が入力されている
↓
商品マスタに P105 があるか確認
```

これは**内容の妥当性**の確認であり、必要な別項目が入力されているかどうかとは別です。

### 論理チェックとフォーマットチェックを混同する

日付を扱っているだけでフォーマットチェックと判断しないようにします。

- `2026/08/27` の形式か → フォーマットチェック
- 開始日 ≤ 終了日か → 論理チェック

**何の値かではなく、何を確認しているか**を見るのがポイントです。

### シーケンスチェックと論理チェックを混同する

どちらも「順番」を扱う場合がありますが、見る対象が異なります。

- **シーケンスチェック**：伝票番号が `001 → 002 → 003` と並び、欠番がないか
- **論理チェック**：注文日が入力日以前など、異なる項目間の関係に矛盾がないか

番号の並びを調べるのか、複数項目の大小関係を調べるのかを確認します。

### 重複チェックとシーケンスチェックを混同する

- 同じ番号が2つある → 重複チェック
- 番号が途中で抜けている → シーケンスチェック

どちらも番号を扱うことがありますが、確認する目的が違います。

### 「数値だから正しい入力」？

違います。数値として正しくても範囲外や業務ルール違反の場合があります。

### 「形式チェックを通れば日付は実在する」？

必ずしもそうではありません。例えば桁や区切り記号が正しくても、2月30日のように存在しない日付が入力される場合があります。

### 「チェックディジットで改ざんを防げる」？

違います。チェックディジットは偶発的な入力・転記誤りの検出が主目的であり、暗号学的な改ざん検知や認証には使えません。

## まとめ（試験直前用）

- **入力漏れ**を見る → 必須チェック・項目数の確認
- **数値として読めるか**を見る → ニューメリックチェック
- **書式・文字種・桁数**を見る → フォーマットチェック
- **境界を守るか**を見る → リミット（片側）・レンジ（上下両側）
- **項目同士の矛盾**を見る → 論理チェック
- **登録済みの値か**を見る → マスタ照合
- **同じデータの存在**を見る → 重複チェック
- **順番・連続性**を見る → シーケンスチェック
- 「何のデータか」ではなく、**何を検出したいか**で選択肢を切る
