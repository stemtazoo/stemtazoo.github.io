## まず結論

ITサービスマネジメントでは、**早く復旧する、原因を調べる、変更を評価する、本番に展開する、構成情報を正しく保つ**という活動を区別します。

| 活動 | 主な目的 | FEの判断キーワード |
|---|---|---|
| インシデント管理 | サービスへの影響を抑え、速やかに復旧する | 障害対応、早期復旧 |
| 問題管理 | 根本原因や既知の誤りを調べ、再発・影響を減らす | 原因分析、再発防止 |
| 変更管理（変更実現） | 変更のリスク・影響を評価し、適切に承認する | 影響評価、変更承認 |
| リリース管理・展開管理 | 新しい／変更されたサービスや構成要素を利用可能にし、適切に本番などへ展開する | リリース、展開、切替え |
| サービス構成管理 | 構成アイテムと関係を正確に把握する | CI、CMDB、構成情報 |

**実際のITサービス管理は、必ずこの順番に一度ずつ進むわけではありません。** 試験では、各活動の目的から判断しましょう。

## 直感的な説明

工場の設備監視システムが突然停止したと考えます。

```text
① 監視システムが停止
   → インシデント管理：予備系への切替えなどで復旧
② 同じ障害が繰り返される
   → 問題管理：原因を分析し、対策を検討
③ プログラムを修正したい
   → 変更管理：影響・リスク・承認を確認
④ 承認された修正版を提供・展開
   → リリース管理・展開管理
⑤ 利用中のバージョンなどを記録
   → サービス構成管理：構成情報を最新に保つ
```

この図は役割を理解するための**一例**です。現場では変更管理と構成管理を並行して行うなど、活動が重なります。

## 定義・仕組み

### まず、インシデント管理と問題管理を分ける

**インシデント管理**は、サービスをできるだけ早く正常な状態へ戻し、業務への影響を減らす活動です。原因が完全に分からなくても、回避策を使って復旧する場合があります。

**問題管理**は、発生済みまたは発生する可能性のあるインシデントの原因を分析し、既知の誤りや回避策を管理します。再発防止につながる恒久的な変更が必要な場合は、変更管理と連携します。

これらの違いは[インシデント管理と問題管理の比較](/fe/incident-management-vs-problem-management/)で詳しく説明しています。

### 変更管理（変更実現）

ITサービスへの変更要求があったとき、**必要性・影響・リスク・予定・承認**などを検討する活動です。

例：監視プログラムを変更することで、別の監視機能に不具合が出ないか、夜間に展開するべきか、切戻しは可能かを確認する。

**「問題の原因が分かったから、すぐ本番プログラムを書き換える」ではありません。** 変更の規模やリスクに応じて適切な手順で扱います。ITIL 4では「変更実現（change enablement）」というプラクティス名も使用されます。

### リリース管理と展開管理の違い

**リリース管理**は、新規または変更されたサービス・機能を利用可能にする活動です。

**展開管理（deployment management）**は、変更されたハードウェア・ソフトウェアなどの構成要素を本番環境等へ移す活動です。

| 場面 | 主に関係する活動 |
|---|---|
| 修正内容を審査し、変更を承認する | 変更管理 |
| 新機能を利用者が使える状態にする計画・調整 | リリース管理 |
| 修正版を本番サーバに配置する | 展開管理 |
| 配置後のバージョンや関連する構成要素を記録する | サービス構成管理 |

**リリース管理＝変更の承認そのものではありません。** また、実際の組織ではリリースと展開を一体として運用することもあります。

### 構成管理とCMDB

**サービス構成管理**では、ITサービスを構成するサーバ、ソフトウェア、設定などの**構成アイテム（CI：Configuration Item）**や、その関係を把握します。

**CMDB（Configuration Management Database）**は、その構成情報を管理するためのデータベースです。

```text
監視サービス
 ├─ Webサーバ：バージョン 2.1
 ├─ データベース：バージョン 5.0
 └─ ゲートウェイ：設定版 3
```

変更後に構成情報が古いままだと、障害調査や次の変更の影響分析を誤る可能性があります。なお、サービス構成管理は単にソースコードの版を記録することだけではありません。

ソフトウェア開発の構成管理との関連は[構成管理とバージョン管理](/fe/configuration-management/)も参照してください。

### サービスレベル管理・可用性管理とのつながり

**SLA**は、利用者とサービス提供者が合意するサービス目標などを定めた合意です。**サービスレベル管理（SLM）**では、その目標を継続的に監視・評価・改善します。

**可用性管理**は、必要なときにサービスが利用できる状態を保つための活動です。復旧や変更を評価するときにも、合意したサービス水準への影響を考慮します。

- [SLAとSLM](/fe/sla/)
- [サービスの可用性](/fe/service-availability/)

## 科目Aでどう出る？

問題文の動詞を見ると、判断しやすくなります。

```text
復旧する → インシデント管理
原因を究明する → 問題管理
変更を評価・承認する → 変更管理
新しい機能を利用可能にする → リリース管理
本番環境に配置する → 展開管理
構成アイテムの情報を更新する → サービス構成管理
サービス目標の合意・測定・改善 → SLA・SLM
```

### 確認問題

本番システムの不具合に対応する修正版が完成した。修正による影響とリスクを評価し、運用への適用を承認する活動として最も適切なのはどれか。

- ア：インシデント管理
- イ：問題管理
- ウ：変更管理
- エ：サービス構成管理

<details markdown="1">
<summary>正解と解説を見る</summary>

**正解：ウ（変更管理）**。変更の影響・リスクを評価し、適切な承認を行うためです。原因分析は問題管理、構成情報の維持はサービス構成管理です。

</details>

## どんな場面で使う？

ITサービスを運用する際、障害発生から修正・展開・構成情報の維持まで、複数の担当者やプラクティスが協力する場面で使われます。実際の運用では、変更の危険度や緊急性に応じて手順が異なるため、**必ず全てを直列に実施するとは限らない**点も重要です。

## よくある誤解・混同

### 「問題管理はサービスをすぐ復旧する担当」？

中心になる目的は根本原因の分析と再発・影響の低減です。速やかな復旧はインシデント管理に注目します。

### 「修正が完成したら変更承認なしですぐリリースする」？

通常はリスクに応じた変更管理の手順が必要です。ただし標準変更・緊急変更など、組織が定めた適切な承認方法は異なります。

### 「CMDBがあれば、構成情報は自動で必ず正しい」？

違います。正確な構成情報を維持する管理活動が必要です。

## まとめ（試験直前用）

- **インシデント管理**：早期復旧と影響軽減。
- **問題管理**：原因分析と再発防止・影響低減。
- **変更管理**：影響評価と承認。
- **リリース／展開管理**：新しい機能を利用可能にする／本番環境に配置する。
- **サービス構成管理**：CIとCMDB、構成情報の維持。
- **SLA／SLM**：サービス水準の合意／継続的な管理。
