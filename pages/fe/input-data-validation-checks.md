## まず結論

**入力チェック（input validation）**は、入力された値が、あらかじめ決めた形式・範囲・業務ルールに合っているかを確かめる仕組みです。

| 種類 | 何を確認するか | 例 |
|---|---|---|
| ニューメリックチェック | 数値として正しい入力か | 数量欄に文字が入っていないか |
| フォーマットチェック | 決められた書式か | 商品コードが英字2文字＋数字4桁か |
| リミットチェック | 上限または下限を超えていないか | 発注数が100以下か |
| レンジチェック（範囲チェック） | 下限と上限の間か | 年齢が0～120か |
| 論理チェック | 項目間や業務上の矛盾がないか | 終了日時が開始日時より前ではないか |
| 必須チェック | 必要な項目が入力されているか | 氏名が空欄でないか |
| 重複チェック | 登録済みの識別子などと重複しないか | 会員番号が既存番号と同じでないか |
| チェックディジット検査 | 番号から計算した検査桁が一致するか | 商品番号の入力誤りを検出 |

「形式は正しいが、意味としてはおかしい」場合もあります。**チェックを組み合わせること**が重要です。

## 直感的な説明

工場の設備点検フォームを考えます。

- 温度欄に「ABC」→ 数値チェックで検出
- 点検日を「2026/99/99」→ 日付としての妥当性確認で検出
- 圧力上限100に対して「150」→ リミットチェックで検出
- 点検終了時刻が開始時刻より前 → 論理チェックで検出

**書き方、値の大きさ、項目間の意味**は別々に確認します。

## 定義・仕組み

### 形式・範囲・論理の違い

| 入力 | 検査 | 判断 |
|---|---|---|
| 数量に「12A」 | ニューメリック | 数値の形式ではない |
| 品番「AB-1234」 | フォーマット | ルールが英字2桁＋ハイフン＋数字4桁なら適合 |
| 数量150、上限100 | リミット | 上限超過 |
| 温度-10、許可範囲0～80 | レンジ | 下限より小さい |
| 開始10:00、終了09:00 | 論理 | 同日の点検なら終了が開始より前 |
| 品番「AB-1234」が登録済み | 重複 | 一意であるべき番号としては不可 |

**リミットチェックは一方の境界、レンジチェックは上下両方の境界**を見ると区別しやすくなります。名称や分類が教材によって多少違うことがありますが、問題文の検査条件を優先しましょう。

### 触って覚える：どのチェックでエラーになる？

それぞれの入力を見て、**どの検査がエラーを検出するか予想してから**答えを開いてください。

<details markdown="1">
<summary>ケース1：数量に「A12」と入力した</summary>

**ニューメリックチェック**。数量欄が数値のみを受け付ける場合、文字が混ざっていることを検出します。

</details>

<details markdown="1">
<summary>ケース2：品番の書式が「英字2文字-数字4桁」なのに「AB1234」と入力した</summary>

**フォーマットチェック**。ハイフンの位置など、定められた書式に合っているかを確認します。

</details>

<details markdown="1">
<summary>ケース3：温度の許可範囲は0～80なのに「90」と入力した</summary>

**レンジチェック**。上限・下限を含む許可範囲から外れています。

</details>

<details markdown="1">
<summary>ケース4：同じ日の作業で、開始が15:00、終了が14:00</summary>

**論理チェック**。入力形式が正しくても項目間の関係が矛盾しています。

</details>

<details markdown="1">
<summary>ケース5：会員番号が既存登録と同じだった</summary>

**重複チェック**。一意でなければならない番号の再登録を検出します。

</details>

### チェックディジットはどこが違う？

**チェックディジット（check digit）**は、識別番号などに規則的な検査用の桁を加え、入力ミスや転記ミスを検出する方法です。番号が実在するか、本人のものか、悪意ある改ざんがないかを保証する仕組みではありません。

計算方法や余り（mod）の問題は[チェックディジットの記事](/fe/check-digit/)で扱っています。

### クライアント側のチェックだけで十分？

十分ではありません。ブラウザ上の入力チェックは利用者のミスを早く伝えるために便利ですが、回避できる場合があります。**サーバ側でも必要な妥当性検査を行う**ことが大切です。

## 科目Aでどう出る？

「何に違反しているか」を読むのがコツです。

```text
文字が混じる → ニューメリック
桁数・記号の並びが違う → フォーマット
上限・下限を超える → リミット
上下の許容範囲を外れる → レンジ
項目同士が矛盾する → 論理チェック
登録済みの番号と一致する → 重複チェック
```

### 確認問題

工場の点検記録で、点検開始日時と終了日時はいずれも正しい日付形式だが、終了日時が開始日時より前であることを検出したい。最も適切なチェックはどれか。

- ア：ニューメリックチェック
- イ：論理チェック
- ウ：フォーマットチェック
- エ：チェックディジット検査

<details markdown="1">
<summary>正解と解説を見る（タップして開く）</summary>

**正解：イ（論理チェック）**。個々の入力の形式は正しくても、2項目の前後関係という業務上の条件が成り立っていません。

</details>

## どんな場面で使う？

予約・注文・在庫・設備点検などの入力画面で、誤入力を早期に見つけるために使われます。入力後に何が間違っているかを利用者に具体的に伝えることも重要です。

## よくある誤解・混同

### 「数値だから正しい入力」？

違います。数値として正しくても範囲外や業務ルール違反の場合があります。

### 「形式チェックを通れば日付は実在する」？

必ずしもそうではありません。例えば桁や区切り記号が正しくても、2月30日のように存在しない日付が入力される場合があります。

### 「チェックディジットで改ざんを防げる」？

違います。チェックディジットは偶発的な入力・転記誤りの検出が主目的であり、暗号学的な改ざん検知や認証には使えません。

## まとめ（試験直前用）

- **ニューメリック**：数値か
- **フォーマット**：書式が合っているか
- **リミット／レンジ**：境界を守っているか
- **論理**：複数項目の関係に矛盾がないか
- **重複・必須**：登録済み番号や空欄を確認
- **チェックディジット**：計算した検査桁で入力誤りを見つける
