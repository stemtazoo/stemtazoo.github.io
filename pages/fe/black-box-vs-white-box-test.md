## まず結論

**ブラックボックステストは入力と出力、ホワイトボックステストはプログラム内部の処理や分岐に着目してテストを設計する方法**です。

基本情報技術者試験では、まず次の基準で選択肢を切ります。

| 問題文の手掛かり | 判断 |
|---|---|
| 仕様、入力値、期待する出力 | ブラックボックステスト |
| 命令、分岐、内部の実行経路、網羅率 | ホワイトボックステスト |
| 入出力は正しいが、不要な処理が残っている | ブラックボックステストだけでは発見しにくい |

**「外から動作を見る」か「中の処理を見る」か**が最初の判断ポイントです。

## 直感的な説明

電卓に「100 + 20」と入力して「120」が表示されたとします。

- **ブラックボックステスト**：入力が100と20なら、出力が120になるかを確かめる
- **ホワイトボックステスト**：計算に至るまでのプログラムの処理や分岐を確認する

電卓の答えが正しくても、内部で同じ計算を何度も繰り返しているかもしれません。

ブラックボックステストは、**外から見える振る舞いが正しいこと**を確認できますが、内部に不要なコードがあるかどうかは、入出力だけでは分かりません。

## 定義・仕組み

### ブラックボックステスト

仕様に基づいて入力と期待結果を決め、実際の出力が一致するかを調べます。テストケースを設計する際に、プログラムの内部構造を前提としません。

代表的な技法は次のとおりです。

- **同値分割**：同じ結果になると考えられる入力をグループに分け、代表値を試す
- **限界値分析**：有効・無効の境界付近を重点的に試す
- **デシジョンテーブル**：複数条件の組合せと期待結果を整理する

例えば「0〜100点を受け付ける」仕様なら、0、100、-1、101などの値を考えます。**仕様上の境界**が手掛かりです。

### ホワイトボックステスト

ソースコードの命令や分岐など、内部構造に着目してテストケースを設計します。

代表的な網羅基準は次のとおりです。

- **命令網羅**：各命令を少なくとも1回実行する
- **判定条件網羅（分岐網羅）**：判定結果の真と偽を確認する
- **条件網羅・複数条件網羅**：判定式を構成する条件や組合せを確認する

網羅基準の詳しい違いは、[ホワイトボックステストの網羅基準](/fe/white-box-test-coverage/)で確認できます。

### Pythonで比べる：出力が正しくても不要な処理は残る

次の関数は、税抜価格から税込価格を求めます。

```python
def total_with_tax(price):
    tax = price * 0.10
    unused = price * 100  # 結果に使われない計算
    return price + tax

assert total_with_tax(1000) == 1100
```

`assert` による確認は成功します。入力1000に対して、期待どおり1100が返るためです。

しかし、`unused = price * 100` は結果に使われていません。

```text
外から見る
1000 → 関数 → 1100
         ↓
      出力は正しい

中を見る
tax を計算
unused を計算 ← 結果に使わない
合計を返す
```

この例で、**期待する出力を確かめる観点はブラックボックステストに相当**します。一方、不要な代入の存在を調べるには内部のコードを見る必要があります。

ただし、不要なコードを見つける方法がホワイトボックステストだけという意味ではありません。**コードレビューや静的解析**も有効です。

## 科目Aでどう出る？

科目Aでは、テストの特徴や限界を説明した選択肢から正しいものを選びます。

| 選択肢に出る表現 | 判断 |
|---|---|
| 入力に対して仕様どおりの結果が得られるか | ブラックボックス |
| 内部の命令や分岐をどれだけ通ったか | ホワイトボックス |
| ソースコードにある不要な処理を必ず見つけられる | ブラックボックスの説明として誤り |
| 命令網羅率を基に入力を選ぶ | ホワイトボックス |

特に重要なのは、**「出力が正しい」ことと「内部のコードに問題がない」ことは別**という点です。

また、分岐が増えるとテストケースが増えやすいという説明は、内部構造に着目したテストで考えると理解しやすくなります。ただし、ブラックボックステストでも仕様上の条件が増えればテストケースが増えることはあります。

## どんな場面で使う？

例えば、会員登録機能を確認する場合です。

**ブラックボックステスト**では、メールアドレスが空欄ならエラーになるか、有効な入力なら登録できるか、といった仕様上の振る舞いを確認します。

**ホワイトボックステスト**では、入力チェックの条件分岐や例外処理など、内部の経路を通るようにテストを設計します。

実務ではどちらか一方だけで十分とは限りません。**異なる観点を組み合わせて、見落としを減らす**ことが重要です。

なお、テスト支援ツールの**静的・動的**という分類は、「プログラムを実行するか」という別の軸です。詳しくは[テスト支援ツールの違い](/fe/test-support-tools/)で整理しています。

## よくある誤解・混同

### ブラックボックステストではバグを見つけられない？

いいえ。期待結果と実際の結果が異なれば、不具合を発見できます。

ただし、**同じ出力になる不要な処理や、テストしていない条件の不具合まで保証するものではありません**。

### ホワイトボックステストなら、すべての不具合が分かる？

いいえ。内部の命令や分岐を網羅しても、仕様そのものの誤解や必要な機能の欠落を見落とすことがあります。

**網羅率100%＝不具合ゼロ**ではありません。

### ブラックボックス・ホワイトボックスは静的・動的と同じ分類？

違います。

```text
ブラックボックス / ホワイトボックス
→ 何を基にテストを設計するか

静的 / 動的
→ プログラムを実行して調べるか
```

例えば、内部の分岐を基にテストを作り、実際にプログラムを動かしてカバレージを測る場合、ホワイトボックステストであり、測定は動的です。

## まとめ（試験直前用）

- **入力・出力・仕様**に着目 → ブラックボックステスト
- **命令・分岐・網羅率**に着目 → ホワイトボックステスト
- 出力が正しくても、内部の不要なコードは残り得る
- **網羅率100%でも、不具合がゼロとは限らない**
- 静的・動的の違いとは**分類の軸が別**

> **外の振る舞いを見るか、中の経路を見るか。まずはここで切り分ける。**
