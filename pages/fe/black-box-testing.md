## まず結論

ブラックボックステストとは、**プログラムの内部処理や内部構造を見ずに、機能仕様や入出力仕様をもとにテストケースを設計する方法**です。

基本情報技術者試験では、**「仕様・入力・出力をもとにテストケースを作る」**という説明が判断の合図です。

```text
仕様・入力・出力を見る
→ ブラックボックステスト
```

内部構造を見るホワイトボックステストとの違いを横並びで確認したい場合は、[ブラックボックステストとホワイトボックステストの違い](/fe/black-box-vs-white-box-testing/) を参照してください。

## 直感的な説明

ブラックボックステストは、**中身が見えない自動販売機を外から試す**イメージです。

例えば、自動販売機の中の配線や制御プログラムは見ません。

見るのは、次のような外から分かる動きです。

- 正しい金額を入れたら商品が出るか
- 金額が足りないときは購入できないか
- 売り切れの商品を選んだときに購入できないか
- おつりが正しく返るか

このように、ブラックボックステストでは **内部でどんな処理をしているか** ではなく、

> **この入力を与えたら、仕様どおりの出力になるか**

に注目します。

## 定義・仕組み

ブラックボックステストは、システムやプログラムの内部構造をテストケース設計の基準にせず、外部から見える機能に注目して行うテストです。

テストケースは、主に次のような情報をもとに設計します。

| 見るもの | ブラックボックステストでの役割 |
|---|---|
| 機能仕様 | どの入力に対して、どの出力になるべきかを確認する |
| インタフェース仕様 | 画面、API、入出力項目などの外から見える仕様を確認する |
| 入力値の範囲 | 正常値、異常値、境界値を決める |
| 期待結果 | 出力、エラー表示、処理結果が仕様どおりかを確認する |

例えば、年齢を入力するシステムについて、仕様が次のようになっているとします。

```text
入力可能な年齢：0～120歳
```

ブラックボックステストでは、ソースコードを読むのではなく、この仕様からテストケースを考えます。

| 入力値 | 確認したいこと |
|---:|---|
| 30 | 正常な範囲の値を受け付けるか |
| 0 | 下限値を受け付けるか |
| 120 | 上限値を受け付けるか |
| -1 | 範囲外として処理されるか |
| 121 | 範囲外として処理されるか |

このように、**仕様から代表的な入力を選び、その出力が正しいか確認する**のが基本です。

### 代表的なブラックボックステストの手法

FE試験では、代表的なテストケース設計手法も整理しておくと判断しやすくなります。

| 手法 | 何を見る？ | 覚え方 |
|---|---|---|
| 同値分割 | 同じように扱われる入力のグループ | 入力をグループに分ける |
| 限界値分析 | 有効・無効の境目 | 境界の直前・境界・直後を見る |
| 状態遷移テスト | 現在状態とイベント | 期待する次状態を確認する |
| デシジョンテーブル | 条件の組合せと結果 | 条件を表で整理する |
| 原因結果グラフ | 入力条件と出力結果の関係 | 原因と結果の組合せを見る |
| エラー推測 | 経験から起こりそうな誤り | 間違いそうなところを狙う |

特に、**同値分割と限界値分析**はセットで整理すると覚えやすくなります。処理が変わる境界の見つけ方や、代表値と境界値の最小個数は、[同値分割と境界値分析：代表値と境界値の選び方](/fe/equivalence-partitioning-boundary-value/) で詳しく確認できます。

### 同値分割

入力値を、同じような結果になるグループに分け、その中から代表値を選びます。

先ほどの `0～120歳` なら、例えば次のように分けられます。

```text
0未満       → 無効なグループ
0～120      → 有効なグループ
121以上     → 無効なグループ
```

すべての値を試すのではなく、各グループから代表値を選ぶ考え方です。

### 限界値分析

不具合は、入力範囲の**境界付近**で起こりやすいため、その周辺を重点的に確認します。

`0～120歳` なら、

```text
-1, 0, 1
119, 120, 121
```

のように境界付近を確認します。

このテーマは、基本情報技術者試験のシステム開発技術やプログラムのテストと関係する内容です。公式の出題範囲やシラバスは、[IPA：基本情報技術者試験](https://www.ipa.go.jp/shiken/kubun/fe.html) から確認できます。


### 状態遷移テスト：現在状態とイベントから期待結果を確認する

**状態遷移テスト（State Transition Testing）**は、仕様で定めた**現在の状態とイベント**に対して、システムが期待どおりの次状態になるかを確認するブラックボックステスト技法です。

例えば、設備制御アプリを次の3状態で設計したとします。

- **停止中**：設備は停止している。
- **運転中**：設備は稼働している。
- **異常停止**：異常検知で停止し、安全確認・復旧を待っている。

以下の表が、この教材で使う**仕様（正しい動作の基準）**です。

| 現在状態 | イベント | 期待する次状態 | 仕様上の扱い |
|---|---|---|---|
| 停止中 | 開始 | 運転中 | 許可される遷移 |
| 運転中 | 停止 | 停止中 | 許可される遷移 |
| 運転中 | 異常検知 | 異常停止 | 許可される遷移 |
| 異常停止 | 安全確認後のリセット | 停止中 | 許可される遷移 |
| 異常停止 | 開始 | 異常停止のまま | **禁止された遷移を拒否する** |

最後の行も大切です。**異常停止中に開始を指示しても運転中に移ってはいけない**という仕様を、実際に確認できます。これは学習用の簡略モデルであり、現実の設備にはさらに多くの安全条件が必要です。

#### ブラックボックスなのに「状態」を見るのはなぜ？

ここでいう状態は、**仕様に定義されたシステムの状態**です。ソースコード内の変数や条件分岐を読んでテストケースを作る、という意味ではありません。

```text
仕様：異常停止中 ＋ 開始指示 → 異常停止のまま
         ↓ 実際に入力
結果：異常停止のままなら合格
      運転中になれば不合格
```

ブラックボックステストかホワイトボックステストかは、**テストケース設計の根拠が外部仕様か内部構造か**で判断します。テスト結果の確認で状態表示やログを使う場合があっても、それだけでホワイトボックステストになるわけではありません。

**実験してみる順番**

1. 「停止中」＋「開始」を実行し、期待状態と実際の状態が一致するか確認する。
2. 「異常停止」＋「開始」を実行し、禁止された遷移が拒否されるか確認する。
3. 同じ条件のまま「不具合を注入する」を選んで、期待状態と実際の状態が不一致になることを確認する。

ここでの不具合注入は**教材内の仮想システムの挙動だけを変更する**機能です。実機やWebサイトの安全装置には作用しません。各テストは選択した状態から独立して実行します。連続したイベント列を追う方法は[状態遷移表](/fe/state-transition-table/)で学べます。

### 状態遷移テストと決定表テストの違い

| 技法 | テストケースの基準 | 主な確認対象 |
|---|---|---|
| **状態遷移テスト** | 現在状態＋イベント | 仕様どおりに次状態へ移るか、禁止された遷移を拒否するか |
| [決定表テスト](/fe/decision-table/) | 複数の条件の組合せ | 各組合せに対する動作が正しいか |
| ホワイトボックスの分岐網羅 | プログラム内部の分岐 | 真側・偽側などを通るか |

関連する図の読み方は[状態遷移図](/fe/state-transition-diagram/)の記事も参照してください。

参考：[ISTQB Foundation Level Syllabus：State Transition Testing](https://astqb.org/4-2-black-box-test-techniques/)。

## 科目Aでどう出る？

科目Aでは、テストケースの設計方法を説明した選択肢から、ブラックボックステストに当てはまるものを判断する問題があります。

そのときは、文章の中で**何を基準にテストケースを作っているか**を確認します。

### ブラックボックステストと判断しやすい言葉

次のような言葉が中心なら、ブラックボックステストを疑います。

- 機能仕様
- インタフェース仕様
- 入力と出力
- 入力範囲
- 同値分割
- 限界値分析
- 状態遷移テスト

反対に、ソースコード・内部構造・分岐・網羅率が中心なら、ブラックボックステストではありません。詳しい比較は[ブラックボックステストとホワイトボックステストの違い](/fe/black-box-vs-white-box-testing/)で整理しています。

大切なのは、**テストを実施する時期ではなく、何を基準にテストケースを設計しているか**です。

また、「冗長なコード」「実行されないコード」「不要な処理」などは、外から見た入出力だけでは直接確認しにくいため、ブラックボックステストだけでは検出しにくい問題です。

### 選択肢を切る順番

似た説明が並んだときは、次の順番で確認します。

```text
1. 機能仕様・インタフェース仕様が基準か？
   → ブラックボックスの候補

2. 入力範囲・境界・期待結果を見ているか？
   → ブラックボックスの可能性が高い

3. ソースコードや内部構造も参照しているか？
   → ブラックボックスだけの説明ではない

4. 実施時期だけを説明していないか？
   → それだけでは判定できない
```

特に、**「仕様書」という言葉だけで決めず、テストケース設計の根拠を見る**ことが重要です。

### 実データの抽出と仕様からのテスト設計を混同しない

ブラックボックステストの選択肢には、「実際の業務データを使う」「発生頻度に合わせて抽出する」といった、もっともらしい説明も登場します。実データや利用頻度を使うテストにも意味はありますが、**それだけで仕様上の有効・無効や境界を十分に確認できるとは限りません**。

例えば、仕様が「入力できる年齢は0～120歳」の場合を考えます。

| テストデータの選び方 | 選ぶ値の例 | 主に確認できること |
|---|---|---|
| 稼働中のデータから無作為抽出 | 実際に登録された年齢 | 実際のデータでの動作。ただし異常値や境界値が含まれる保証はない |
| 業務上の発生頻度を考慮 | 利用者に多い年齢層 | よく使われる条件での動作。ただし珍しい異常値を見落とし得る |
| **仕様から同値分割** | -1、30、121 | 有効・無効の各クラスの代表例 |
| **仕様から限界値分析** | -1、0、1、119、120、121 | 入力可能範囲の境目 |

この表の値は選び方を示す例であり、実データの無作為抽出や頻度を考慮したテストが無意味ということではありません。目的によっては有効です。

ただし、**「ブラックボックステストの代表的なテストデータ設計手法はどれか」**と問われたら、機能仕様から同値クラスや境界値を識別する説明を優先します。

また、「プログラムの流れ図から分岐条件を選ぶ」は内部構造に基づくため、ホワイトボックステストの考え方です。

## 科目Bでどう使う？

科目Bでは、プログラムのテストやデバッグを考える場面で、仕様から必要なテストケースを読み取る考え方が役立ちます。

例えば、次の仕様があるとします。

```text
入力 x が 1～100 のときだけ処理を行う。
それ以外はエラーとする。
```

この場合、まず仕様から境界を見つけます。

```text
下限：1
上限：100
```

次に、その前後を含めて確認します。

```text
0, 1, 2
99, 100, 101
```

ここで重要なのは、プログラム内部の `if` 文がどう書かれているかを推測することではありません。

**仕様に対して、どの入力を試せば正常・異常の境界を確認できるか**を考えます。

科目Bでテストケースを読むときは、次の順番で整理すると分かりやすくなります。

1. 入力条件を確認する
2. 正常な範囲と異常な範囲を分ける
3. 境界値を見つける
4. 境界の前後をテストする
5. 期待する出力と実際の結果を比較する

## よくある誤解・混同

### 誤解1：プログラム完成後に行うテストがブラックボックステスト

ブラックボックステストかどうかは、**いつ実施するか**だけでは決まりません。

判断するポイントは、テストケースを設計するときに何を見るかです。

```text
機能仕様・入出力仕様を見る
→ ブラックボックステスト

内部構造・処理手順を見る
→ ホワイトボックステスト
```

したがって、「コーディングが終わった後だからブラックボックス」とは判断できません。

### 誤解2：条件判定をテストするならブラックボックステスト

「条件」という言葉だけでは判断できません。

例えば、入力できる値の範囲を仕様から確認するならブラックボックステストです。

一方で、プログラム内部の条件式について、真側と偽側の分岐を通るか確認するならホワイトボックステストです。

この違いは、[判定条件網羅（分岐網羅）とは？](/fe/branch-coverage/) と比べると整理しやすくなります。

| ブラックボックステスト | ホワイトボックステスト |
|---|---|
| 外部仕様を見る | 内部構造を見る |
| 入力と出力に注目 | 処理手順や分岐に注目 |
| 同値分割・限界値分析など | 命令網羅・分岐網羅など |

### 誤解3：すべての入力値を試す

ブラックボックステストは、すべての入力を総当たりで試すという意味ではありません。

入力できる値が非常に多い場合、すべてを試すのは現実的ではありません。

そこで、同値分割で代表値を選んだり、限界値分析で境界付近を重点的に確認したりします。

### 誤解4：ブラックボックステストなら内部の無駄なコードも見つけられる

ブラックボックステストでは、プログラム内部の構造そのものを確認しません。

そのため、

- 冗長なコード
- 実行されないコード
- 不要な処理

などが内部に残っていても、**外から見た入出力が仕様どおりなら、それ自体を直接検出できないことがあります**。

こうした内部構造上の問題を確認するには、ソースコードや命令・分岐などに着目するホワイトボックステスト側の考え方が必要です。

違いで迷ったら、[ブラックボックステストとホワイトボックステストの違い](/fe/black-box-vs-white-box-testing/) で判断基準を横並びに確認できます。

ブラックボックステストを理解したら、次に [ホワイトボックステストとは？](/fe/white-box-testing/) を読むと、「外から見るテスト」と「中を見るテスト」の違いをつなげて学べます。

## まとめ（試験直前用）

- ブラックボックステストは、**内部構造を見ず、機能仕様や入出力仕様をもとにテストする**
- 「仕様・入力・出力」が中心ならブラックボックスを疑う
- 「内部構造・処理手順・分岐・網羅率」が中心ならホワイトボックスを疑う
- 冗長コードや実行されないコードの検出は、ブラックボックステストだけでは難しい
- 同値分割は **入力をグループ分け**、限界値分析は **境界付近を確認**する
- 状態遷移テストは **仕様上の現在状態＋イベント→期待する次状態** を確認する
- 迷ったら「テストケースを作るためにプログラムの中身を見る必要があるか？」で判断する
