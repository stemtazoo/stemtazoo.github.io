## まず結論

利用者IDとパスワードを適切に管理するには、**「誰にアカウントを発行するか」と「本人だけが使えるようにするか」**の両方を確認します。

FE科目Aでは、次の順番で判断すると選択肢を切りやすくなります。

~~~text
発行・権限付与 → 正式な申請と承認を経る
利用中         → 本人が安全にパスワードを変更できる
異動・退職     → 不要な権限やIDを停止・削除する
保管           → 管理者も平文パスワードを一覧保管しない
~~~

**管理が楽になる方法でも、本人確認や承認を省いてよいわけではありません。**

このページは、利用者IDとパスワードの**運用方法の適否**を扱います。パスワードを安全に保存して照合する技術は、[パスワードのハッシュ保存](/fe/password-hash-authentication/)で学べます。

## 直感的な説明

社内システムに新入社員が加わる場面を考えましょう。

アカウントは「建物に入る社員証」、パスワードは「本人しか知らない鍵」に似ています。

- **入社**：責任者の承認を受けて、その人用のIDを発行する
- **在籍中**：必要な業務だけ許可し、パスワードを本人が安全に変更できるようにする
- **異動**：不要になった権限を取り消す
- **退職**：IDを停止・無効化し、再び使われないようにする

たとえ未使用のIDが見つかっても、それを新入社員にそのまま渡すと、以前の利用者とのひも付けや操作記録が混乱するおそれがあります。

**IDは誰が使うかを追えること、パスワードは本人以外に知られないこと**が大切です。

## 定義・仕組み

### 利用者IDは「誰か」を識別する

利用者ID（アカウント名）は、システム上で利用者を識別するための情報です。利用者本人との対応関係を管理し、必要な権限を付与します。

| 管理する場面 | 基本的な対応 |
|---|---|
| 新規発行 | 利用者・必要性・権限を確認し、申請と承認に基づいて有効化する |
| 異動・担当変更 | 現在の業務に必要な権限へ見直す |
| 退職・契約終了 | 不要なIDや権限を速やかに停止・削除する |
| IDの再利用 | 旧利用者とのひも付けや記録の混同を防ぐ。安易な使い回しは避ける |

**アカウントの事前準備**と**利用できる状態への有効化**は別です。発行準備を先に行う場合でも、正式な承認なく利用可能にすることは避けます。

### パスワードは「本人か」を確認する

パスワードは本人確認に使う秘密情報です。次のように管理します。

- 本人が適切な認証・本人確認を経て変更できる
- 漏えいが疑われた場合、変更や無効化により被害を抑える
- 管理者が各利用者の平文パスワードを一覧で読める形にしない
- システム側ではパスワード専用の方式でソルト付きハッシュなどを保存する

管理者が**利用者IDの台帳を管理すること自体**は問題ではありません。危険なのは、IDと対応する**秘密のパスワードまで平文で一覧保管する**ことです。

パスワードの保存・照合の仕組みは[ハッシュ認証の記事](/fe/password-hash-authentication/)で確認できます。

### 現在のパスワード変更の考え方

「本人が必要なときに変更できる」と「一定期間ごとの変更を強制する」は別です。

米国NISTの[SP 800-63B-4（2025年）Password Verifiers](https://pages.nist.gov/800-63-4/sp800-63b/authenticators/#password-verifiers)は、**理由のない定期変更を要求しない**一方、認証情報の侵害を示す証拠がある場合は変更を要求するとしています。

この指針は、2005年の過去問にそのまま書かれているルールではなく、**現在の安全な認証設計を考えるための参考**です。試験では、本人による適切な変更を可能にするかどうかを見ます。

## 科目Aでどう出る？

選択肢の表現だけで決めず、**本人確認・承認・秘密の保護・追跡可能性**のどれに関係するかを考えます。

| 運用例 | 判断と理由 |
|---|---|
| 長く使われていない他人のIDとパスワードをそのまま渡す | **不適切**。旧利用者との対応関係が残るおそれ |
| トラブル対応のため、IDと平文パスワードの一覧表を管理者が保管 | **不適切**。漏えいやなりすましのリスク |
| 本人確認を経て、利用者が自分のパスワードを変更 | **適切**。秘密情報を管理できる |
| 承認前の利用者に、すぐログインできるIDと仮パスワードを渡す | **不適切**。権限付与の承認を省いている |
| 異動・退職に合わせて利用権限やアカウントを見直す | **適切**。不要な権限を残さない |

「新規IDを発行する」「変更を許可する」だけでなく、**誰が承認するか、本人だけが変更できるか**も見落とさないようにします。

### 確認問題

社内の販売管理システムで、利用者アカウントの運用方法として最も適切なものはどれでしょうか。

- ア．手続きを減らすため、退職者のIDとパスワードを次の社員に渡す。
- イ．管理者がログイン代行できるよう、全社員のパスワードを平文で保管する。
- ウ．本人確認を経た利用者が、自分のパスワードを安全に変更できるようにする。
- エ．利用開始を早めるため、申請・承認がない段階でアカウントを有効化する。

<details markdown="1">
<summary>▶ 答えと理由を確認する</summary>

**正解：ウ**

- ア：別の利用者への認証情報の引継ぎは、なりすましや操作記録の混乱を招き得ます。
- イ：管理者に平文の秘密情報を集めることは、漏えい時の被害を大きくします。
- ウ：本人が適切な確認を経て変更でき、漏えい時にも対応できます。
- エ：利用者の準備状況にかかわらず、承認前に利用を許可するのは不適切です。

**「便利か」ではなく「本人性と承認が守られているか」で切る**ことがポイントです。

</details>

## どんな場面で使う？

人事異動の多い会社、複数の業務システムを使う会社、外部委託先に期間限定でアカウントを付与する場面などで役立ちます。

例えば外部委託先の作業者にIDを発行する場合も、必要な作業範囲と利用期限を確認し、終了時には利用できない状態へ変更します。

アカウントを持てる人を適切に管理するのが**ID管理**、そのアカウントで何ができるかを制限するのが**権限管理**です。

関連して、[コンピュータ不正アクセス対策基準](/fe/computer-unauthorized-access-countermeasure-standard/)ではIDの共有禁止や最小権限との関係を説明しています。

SG試験で発行・変更・削除の運用全体を詳しく学ぶ場合は、[ID管理（アカウント管理）](/sg/id-management/)も参考になります。

## よくある誤解・混同

### 未使用のIDなら、そのまま他人に渡してよい？

**安易な再利用は避けます。** 利用者が変わったことを正しく管理できないと、以前の利用者の権限やログとの混同が起こります。

ただし、**識別子を再利用すること自体がすべてのシステムで法律上禁止される、という意味ではありません**。旧利用者との関連を適切に切り離せるかなど、実際の運用ルールによります。

### 管理者はパスワードを知らないと運用できない？

**不要です。** 管理者はID・権限の管理やパスワードの安全な再設定を行えます。平文パスワードを一覧管理する必要はありません。

### 「いつでも変更できる」なら本人確認なしでよい？

**違います。** ログイン中の再認証や適切な本人確認など、権限のない人が変更できない仕組みが必要です。

### 安全のため毎月必ず変更させる？

**必ずしも適切ではありません。** 現在のNIST指針では、理由のない定期変更は要求しません。**漏えいの疑いがあるときに変更する**ことと区別します。

### 仮パスワードなら、正式承認前に利用させてもよい？

**違います。** 仮パスワードであっても、承認されていないアカウントの利用を許可することは避けます。事前準備と利用開始を混同しないことが重要です。

## まとめ（試験直前用）

- **発行・利用開始**：申請・承認を確認する
- **IDの管理**：利用者との対応を保ち、不要になったら停止・削除する
- **パスワード**：本人が安全に変更でき、管理者は平文一覧を保管しない
- **定期変更と漏えい時の変更**：同じものとして判断しない
- **選択肢**：便利さより、本人確認・承認・秘密の保護を優先する
